# ТЗ: Подключение мастеров к ЮKassa через Partners API (OAuth)

## Цель

Каждый мастер на okno.business подключает свой личный аккаунт ЮKassa через OAuth прямо в интерфейсе платформы. После подключения оплата клиента (предоплата за услугу) уходит напрямую в магазин мастера в ЮKassa, минуя расчётный счёт платформы.

Это MVP-этап предоплаты (до перехода на Split Payments, для которого нужен оборот от 3 млн ₽/мес).

---

## Как это работает (общая механика)

1. Платформа регистрирует своё приложение на OAuth-сервере ЮKassa → получает `Client ID` и `Client Secret`.
2. Мастер на своей странице настроек нажимает «Подключить ЮKassa» → редиректится на `https://yookassa.ru/oauth/v2/authorize` → логинится в своём аккаунте ЮKassa → подтверждает доступ.
3. ЮKassa редиректит мастера обратно на Callback URL платформы с одноразовым кодом подтверждения (живёт 5 минут).
4. Бэкенд платформы обменивает код на `access_token` мастера через POST на `https://yookassa.ru/oauth/v2/token`.
5. Токен сохраняется в БД (зашифрованным), привязанным к профилю мастера.
6. При оплате клиентом услуги платформа создаёт платёж через API ЮKassa с заголовком `Authorization: Bearer <токен_мастера>` вместо обычной пары shopId+secretKey — деньги идут прямо в магазин мастера.

**Важное условие:** у мастера уже должен быть собственный магазин (аккаунт) в ЮKassa — регистрируется мастером самостоятельно как ИП или самозанятым, до начала OAuth-подключения.

---

## Регистрация приложения на стороне ЮKassa (разовая настройка, не код)

Через личный кабинет ЮKassa зарегистрировать приложение okno.business:
- Название и описание приложения (видно мастеру на экране подтверждения доступа).
- Ссылка на сайт.
- Callback URL: `https://okno.business/api/yookassa/oauth/callback` (уточнить финальный путь при реализации).
- Права доступа (scope): создание и просмотр платежей — минимально необходимый набор.

Получить и сохранить в переменных окружения:
- `YOOKASSA_OAUTH_CLIENT_ID`
- `YOOKASSA_OAUTH_CLIENT_SECRET`

Начать с тестового приложения/тестового магазина, затем перейти на боевой режим.

## Схема данных (Supabase)

### Таблица `master_yookassa_accounts`

| Поле | Тип | Описание |
|---|---|---|
| id | uuid, PK | |
| master_id | uuid, FK → masters.id | |
| yookassa_account_id | text | `account_id` магазина мастера из ответа `/v3/me` |
| access_token | text (encrypted) | OAuth-токен мастера |
| token_expires_at | timestamptz | из поля `expires_in` при получении токена |
| is_test_shop | boolean | тестовый магазин или боевой |
| payment_methods | jsonb | доступные способы оплаты магазина (из `/v3/me`) |
| status | text | enabled / disabled / revoked |
| connected_at | timestamptz | |
| revoked_at | timestamptz, nullable | |

Токен хранить зашифрованным (например, через Supabase Vault или pgcrypto), не в открытом виде.

### Изменение в таблице `bookings` / `payments`

Добавить поле `master_yookassa_account_id` (FK), чтобы при создании платежа явно знать, через чей токен его проводить.

## Флоу на фронте (мастер)

**Страница настроек мастера → блок «Приём предоплаты»:**

1. Если аккаунт не подключен: кнопка «Подключить ЮKassa» + короткое пояснение, что деньги будут приходить мастеру напрямую, платформа их не удерживает.
2. По клику — редирект на `/oauth/v2/authorize?response_type=code&client_id=...&state=<master_id>` (state = ID мастера в нашей БД, для сопоставления при коллбэке).
3. После успешного коллбэка — статус в интерфейсе меняется на «Подключено ✅», показать `account_id` и доступные способы оплаты.
4. Кнопка «Отключить» — вызывает revoke-token и обновляет статус на `revoked`.

**Экран клиента (оплата предоплаты):**
Без изменений в UX — просто на бэкенде платёж проводится через токен мастера вместо общего аккаунта платформы.

---

## Бэкенд: обработчики

1. **`GET /api/yookassa/oauth/start?master_id=...`** — формирует redirect URL на `/oauth/v2/authorize` с нужным `state`.

2. **`GET /api/yookassa/oauth/callback`** — принимает `code` и `state`:
   - Обменивает `code` на `access_token` через POST на `https://yookassa.ru/oauth/v2/token` (Basic Auth: client_id:client_secret, `grant_type=authorization_code`).
   - Делает `GET https://api.yookassa.ru/v3/me` с полученным токеном, чтобы получить `account_id`, `test`, `payment_methods`, `status`.
   - Сохраняет всё в `master_yookassa_accounts`.
   - Редиректит мастера обратно в интерфейс на страницу настроек с сообщением об успехе/ошибке.

3. **Создание платежа за предоплату:**
   - Найти `master_yookassa_accounts` по `master_id` брони.
   - Если нет подключённого аккаунта или статус не `enabled` — не показывать клиенту оплату через ЮKassa (fallback: сообщение мастеру подключить ЮKassa, либо запись без предоплаты).
   - Провести `POST /v3/payments` с `Authorization: Bearer <access_token мастера>`.

4. **`POST /api/yookassa/oauth/revoke`** — отзыв токена + обновление статуса на `revoked`.

## Обработка ошибок и edge cases

- **Мастер отозвал доступ вручную в ЮKassa** (не через нашу кнопку) — платёж по этому токену вернёт ошибку авторизации. Нужен catch на этот случай → пометить аккаунт как `revoked` и уведомить мастера через Telegram-бот/SMS подключить заново.
- **Тестовый магазин** — если `test: true` в ответе `/v3/me`, доступны только банковская карта и ЮMoney как способы оплаты, и платежи не настоящие. Не давать клиентам платить через тестовый магазин мастера — либо скрывать оплату, либо явно предупреждать в админке мастера, что магазин ещё тестовый.
- **Истечение токена** — проверять `token_expires_at`, обрабатывать как revoked при истечении.
- **Возвраты** — возврат платежа тоже должен идти через токен того же мастера (тот же Bearer-токен, соответствующий эндпоинт возвратов).

---

## Открытые вопросы (уточнить у ЮKassa/по ходу реализации)

- Какой набор прав (scope) оптимален — только платежи или сразу добавить возвраты/чеки в один запрос доступа.
- Формат идентификации мастера в `state` — не передавать чувствительные данные, использовать непрозрачный ID.
- Нужно ли отдельное юридическое соглашение с ЮKassa для Partners API (помимо обычного статуса ИП на НПД).
