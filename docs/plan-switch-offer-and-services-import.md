# План: «Переход с другого сервиса» — импорт услуг и бонус

Статус: черновик плана, 2026-10-21. Разведка по YCLIENTS и DIKIDI учтена.

## Зачем

До запуска главный барьер для мастера с YCLIENTS или DIKIDI — переезд, а не
цена. Снимаем его двумя вещами:

1. **Импорт услуг за минуту**, без ожидания администратора. Доступен всем, не
   только переходящим: новому мастеру он тоже экономит время на первом запуске.
2. **Бонус за переход:** +2 месяца к подписке при первой оплате. Начисляется
   после ручного одобрения заявки в админке. Бонус и импорт не зависят друг от
   друга — мастер работает сразу, одобрение идёт фоном.

Импорт клиентов (CSV/XML) делается отдельно, в этот план не входит.

## Как это выглядит для мастера

1. Регистрация → после создания профиля шаг «Добавьте услуги» с тремя
   вариантами: «Вручную», «Вставить прайс текстом», «Загрузить фото или
   скриншот прайса».
   Тот же вход есть в настройках, вкладка «Услуги» → «Импортировать».
2. Мастер вставляет текст или загружает картинку → 5–15 секунд ожидания →
   таблица найденных услуг: название, цена, длительность, описание, чекбокс
   «добавить».
3. Мастер правит строки (цена «от» помечена, пустая длительность подсвечена и
   требует значения), снимает лишнее, жмёт «Добавить N услуг».
4. Услуги создаются обычным путём — той же валидацией, что и при ручном
   добавлении. Предоплата при импорте не включается: её мастер включает потом
   сам, по тарифу и с подключённой ЮKassa.
5. Отдельно (необязательное поле на том же шаге или в настройках): «Переходите
   с другого сервиса? Ссылка на вашу страницу там» → создаётся заявка на бонус.

Проверку результата делает мастер, а не админ: это его услуги, и ему виднее.

## Импорт через AI (текст или картинка) — основной способ

### Где живёт код

- `src/lib/services-import/extract.ts` — вызов Claude и разбор ответа.
- `src/lib/services-import/schema.ts` — zod-схема результата и нормализация.
- `src/app/actions/services-import.ts` — server action:
  `extractServicesAction` (вход: текст или картинка; выход: черновые строки)
  и `createImportedServicesAction` (вход: подтверждённые мастером строки).
- UI: `src/components/forms/services-import.tsx` — вкладки «Текст» / «Фото»,
  таблица-редактор, используется на шаге регистрации и в настройках.

Ничего не пишем в базу до подтверждения мастера: черновик живёт только в
состоянии формы.

### Вызов модели

- SDK: `@anthropic-ai/sdk`, тот же способ создания клиента, что в
  `src/lib/client-return-message.ts` (ключ `env.anthropicApiKey`, тот же
  сетевой маршрут, что у остальных вызовов из РФ — см. `docs/ru-egress-proxy.md`).
- Модель: по умолчанию `claude-opus-5-5`. Задача — разбор прайса, а не
  рассуждения, поэтому `output_config.effort: "low"`. Если цена станет
  важна — сравнить на 20–30 реальных прайсах с более дешёвой моделью; решение
  за основателем.
- Ответ — структурированный вывод (`output_config.format` с JSON-схемой,
  либо `client.messages.parse()`), без парсинга текста регулярками.
- Обработать `stop_reason`: `refusal` и `max_tokens` → понятная ошибка мастеру
  («Не получилось разобрать прайс, попробуйте вставить текстом»).
- `max_tokens` с запасом: 100 услуг × ~60 токенов ≈ 6000, ставим 16000.

### Схема результата

```ts
{
  services: Array<{
    title: string;                 // как в прайсе, без лишних пробелов
    price: number | null;          // в рублях; null — цены нет
    priceIsFrom: boolean;          // «от 1500»
    priceMax: number | null;       // для диапазона «1500–2500»
    durationMinutes: number | null;// null — в прайсе нет
    description: string;           // «включает покрытие», пусто если нет
    category: string | null;       // заголовок раздела прайса: «Маникюр», «Брови»
  }>;
  warnings: string[];              // «часть цен в долларах», «нечитаемый фрагмент»
}
```

Нормализация после модели (в коде, не в промпте):
- `title` обрезаем, пустые и дубли выкидываем;
- длительность приводим к диапазону 5–480, иначе `null` → мастер заполнит;
- цена < 0 или нечисловая → `null`;
- `category` пока не храним в базе (поля нет) — используем для группировки в
  таблице и как префикс сортировки.

### Промпт (суть)

- Системный: «Ты разбираешь прайс-лист бьюти-мастера. Верни только услуги,
  которые есть в тексте или на изображении. Ничего не придумывай: если нет
  цены или длительности — null. Не переводи и не переименовывай услуги.»
- Вход недоверенный (мастер может вставить что угодно): текст прайса передаём
  внутри явных тегов как данные, инструкции из него не выполняем.

### Картинки

- Форматы: JPEG, PNG, WebP; одна картинка за раз (позже — до 3 для длинных
  прайсов).
- Сжимать на клиенте до ~1600 px по длинной стороне перед отправкой: меньше
  токенов, быстрее загрузка. Лимиты API на размер изображения проверить по
  актуальной документации при реализации.
- Картинку не сохраняем: она нужна только на время разбора.

### Лимиты и защита

- Только для залогиненного мастера.
- Rate limit: например 10 разборов в час и 30 в сутки на профиль (по образцу
  лимитов в `src/app/api/service-consultation/route.ts`).
- Размер текста: до ~20 000 символов; больше — просим разбить.
- Логируем количество токенов и длительность (без содержимого прайса).

### Создание услуг

- `createImportedServicesAction` принимает массив подтверждённых строк, валидирует
  каждую `serviceSchema` из `src/app/actions/settings.ts` (вынести её в общий
  модуль), пишет одним `insert` с `sort_order` по порядку в таблице.
- Предоплата всегда `none`, `bufferMinutes` и `repeatIntervalDays` — 0.
- Ограничение: до 200 услуг за один импорт.

## Импорт по ссылке (YCLIENTS / DIKIDI) — отменён

**Решение 2026-10-22: не делаем.** Для API YCLIENTS нужен свой partner-токен,
то есть партнёрство с конкурентом, которого мы уводим клиентов; ключ мастера
этого не обходит (закрытые методы требуют оба токена) и даёт доступ ко всей
его клиентской базе. DIKIDI запрещает парсинг. Переезд закрывает AI-импорт из
скриншота или PDF. Ссылка на страницу в другом сервисе остаётся только как
подтверждение для бонуса. Разведка ниже сохранена для истории.

Разведка 2026-10-21: оба сервиса отдают услуги простым GET с JSON, браузер не
нужен. Но условия у них разные.

### YCLIENTS — делать, через официальный API

- Метод `GET https://api.yclients.com/api/v1/book_services/<companyId>` —
  документированный, заголовки `Authorization: Bearer <partner token>`,
  `Accept: application/vnd.yclients.v2+json`. С `?staff_id=` — длительность и
  точная цена по сотруднику; сотрудники — `GET /api/v1/book_staff/<companyId>`.
- Из ссылки в ID: `/company/(\d+)` в пути; если в ссылке только ID формы
  (`n<formId>.yclients.com`) — `GET /api/v1/bookform/<formId>` → `company_id`.
- Поля: `title`, `price_min`/`price_max` (диапазон), `comment` (описание),
  категория через `category_id`, `seance_length` (сек., только со `staff_id`).
- **Токен — только свой**, из маркетплейса интеграций YCLIENTS
  (developers.yclients.com). Не использовать токен, зашитый в их виджет:
  его могут сменить, а извлечение из бандла близко к запрету декомпиляции
  в лицензионном договоре. Получение токена — действие основателя.
- Лимит API: 5 запросов в секунду с IP. HTML-страницы не парсить (защита
  ServicePipe, непредсказуемые 403).
- Длительность: если у мастера один сотрудник — берём по его `staff_id`;
  если салон — берём минимальную по сотрудникам и показываем на проверку.
- Надёжность (оценка разведки): 4 из 5 со своим токеном.

### DIKIDI — не делать автоматически

- Технически работает (внутренний `mobile/ajax/newrecord/company_services`,
  без токенов), но **пользовательское соглашение DIKIDI прямо запрещает
  парсинг** любым ПО, а публичного API нет. Эндпоинты внутренние и могут
  исчезнуть без предупреждения.
- Решение по умолчанию: ссылку на DIKIDI принимаем только как подтверждение
  для бонуса. Для импорта услуг предлагаем скриншот страницы DIKIDI → AI-импорт.
  Подсказка в интерфейсе: «Сделайте скриншот списка услуг на вашей странице
  DIKIDI и загрузите его здесь».
- Пересмотреть, если DIKIDI откроет API. Юридическое решение — за основателем.

### Общее

- `src/lib/services-import/sources/yclients.ts` — разбор ссылки, запросы,
  приведение к той же схеме, что у AI-импорта; ответы валидируются zod.
- Ошибка или пустой результат (компания неактивна — `services` пустой) →
  «Не получилось прочитать страницу, загрузите скриншот прайса».
- Результат всегда идёт в ту же таблицу на проверку мастеру.
- Мониторинг: ежедневная проверка на 1–2 известных публичных компаниях
  (статус, наличие полей, непустой список), алерт администратору в Telegram;
  в импорте логировать долю 4xx и пустых ответов.

## Бонус за переход

### Данные

Новая таблица `switch_offer_claims`:
- `id`, `profile_id` (уникально — одна заявка на аккаунт), `source_url`,
  `source_kind` (`yclients` | `dikidi` | `other`), `status`
  (`pending` | `approved` | `rejected` | `granted`), `reviewed_by`,
  `reviewed_at`, `granted_at`, `created_at`.
- RLS: мастер видит и создаёт только свою заявку; меняет статус только сервис.
- Миграция — в `supabase/migrations`, применяется на свой Supabase через docker psql
  (см. `docs/self-hosted-supabase.md`).

### Правила

- Подать заявку можно в первые 30 дней после регистрации.
- `approved` — администратор проверил ссылку в админке.
- `granted` — при **первой** успешной оплате подписки добавляем 60 дней к
  `subscription_until` (той же функцией, что начисляет реферальные +30 дней,
  в одной транзакции с активацией подписки). Если заявку одобрили уже после
  первой оплаты — начисляем сразу при одобрении.
- Отклонённую заявку подать повторно нельзя; мастеру уходит уведомление с
  причиной.

### Админка

- `src/app/(admin)/admin/switch-claims/page.tsx`: список заявок `pending`,
  ссылка открывается в новой вкладке, кнопки «Одобрить» / «Отклонить» с причиной.
- Уведомление администратору в Telegram о новой заявке.
- Аудит-лог действий (таблица `audit_logs` уже есть).

### Тексты

- Лендинг и тарифы: «Уже работаете в другом сервисе записи? Перенесите услуги
  за минуту, а при первой оплате получите ещё 2 месяца в подарок».
- В рекламе и на сайте **не называть конкурентов** (38-ФЗ «О рекламе»,
  некорректное сравнение). Названия YCLIENTS и DIKIDI — только в подсказке у
  поля ссылки.
- Обращение на «вы» (см. `.agents/product-marketing.md`).

## Порядок работ

1. AI-импорт из текста: схема, вызов, таблица-редактор, создание услуг —
   в настройках «Услуги».
2. AI-импорт из картинки.
3. Встроить импорт в регистрацию (шаг после профиля).
4. Бонус: таблица, заявка, админка, начисление при первой оплате, тексты.
5. ~~Импорт по ссылке YCLIENTS / DIKIDI~~ — отменён 2026-10-22 (см. раздел
   «Импорт по ссылке»). Вместо него — длинные прайсы: PDF и длинные скриншоты.

## Как проверить

- 20–30 реальных прайсов разного вида (скриншоты YCLIENTS, DIKIDI, сторис,
  фото прайса на стене, текст из заметок): доля услуг, распознанных без
  правок, и сколько придуманных строк (должно быть 0).
- Unit-тесты нормализации (`schema.ts`): диапазоны, «от», мусорные строки, дубли.
- Начисление бонуса: одобрено до оплаты / после оплаты / отклонено / повторная
  заявка; два одновременных вебхука оплаты не начисляют бонус дважды.

## Открытые вопросы

- Стоимость разбора на одном прайсе — замерить на первом прототипе.
- Нужно ли поле категории услуг в базе (для страницы записи это полезно и
  само по себе).
- Подсвечивать ли на странице записи «цена от», если мастер её оставил.
