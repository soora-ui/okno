# Локальная база

Локальная разработка работает с копией боевой базы в Docker (`supabase start`),
а не с облачным проектом Supabase: облако — устаревшая копия от 2026-10-05,
прод живёт на своём сервере (docs/self-hosted-supabase.md).

## Команды

| Команда | Что делает |
|---|---|
| `npm run db:start` | Поднять локальный Supabase (нужен запущенный Docker Desktop) |
| `npm run db:sync` | Снять свежую копию с прода и развернуть локально (~10 с) |
| `npm run db:sync -- --keep` | Развернуть последний скачанный дамп ещё раз, без похода на сервер |
| `npm run db:apply -- <файл.sql>` | Применить новую миграцию только к локальной базе |
| `npm run db:stop` | Остановить стек |

`db:sync` копирует схему и данные `public`, пользователей `auth` (вход под теми
же почтами и паролями, что на проде), бакеты и файлы `storage`. Прод только
читается. Локальная база заменяется целиком: всё, что было создано в ней
раньше, пропадает. Нужен SSH-ключ `~/.ssh/okno_deploy`.

## Адреса

- API: `http://127.0.0.1:54321` — в `.env.local` (`NEXT_PUBLIC_SUPABASE_URL` и
  стандартные локальные ключи из `supabase status -o env`)
- Postgres: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`,
  или `docker exec -it supabase_db_okno psql -U postgres`
- Studio: `http://127.0.0.1:54323`
- Письма (Mailpit): `http://127.0.0.1:54324`

Облачные значения ключей сохранены в `.env.cloud.local`.

## Правила для агентов

- Данные смотреть и менять в локальной базе. MCP-коннектор Supabase смотрит в
  устаревшее облако — для данных и миграций его не использовать.
- Новая миграция: сначала `npm run db:apply` локально, на прод — только с
  явного согласия пользователя (docs/self-hosted-supabase.md).
- Если код читает колонку, которой нет в копии, значит миграция ещё не на
  проде: примени её локально через `db:apply`.
- В копии настоящие телефоны и почты. `.env.local` использует боевые ключи
  SMS и почты, поэтому не запускай рассылки и напоминания на всю базу.
  Демо-аккаунты (`demo-*@okno.test`) — для экспериментов.
