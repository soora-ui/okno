# Транзакционная почта okno (Unisender Go)

Письма уходят через Web API Unisender Go, не через SMTP: HTTPS-запрос надёжнее
исходящего соединения на 587 порт и сразу возвращает `job_id`, по которому
потом опознаются вебхуки о доставке. Отправитель — домен `mail.okno.business`.

## Что нужно один раз

1. **Домен подтверждён** в Unisender Go: запись владения `confirmed`, DKIM
   `active`. Проверяется скриптом ниже.
2. **Домен ссылок (домен трекинга) настроен.** Без него отправка не работает
   вовсе: `email/send.json` отвечает `403`, API-код `229` — «Custom backend
   domain or tracking domain required for sending». Unisender Go по умолчанию
   переписывает все ссылки на трекинговые, и без своего домена переписывать их
   не на что. Настройки → Домены ссылок → «+» → `link.mail.okno.business`,
   внести выданные DNS-записи, дождаться статуса «Настроен» (до 48 часов).
   Отдельного API-метода нет, только панель: https://godocs.unisender.ru/tracking-domains
3. **API-ключ** — https://go2.unisender.ru/ru/settings/security/api
4. **Переменные окружения** — в `.env.local` и в окружение systemd-сервиса
   на VPS:

```bash
UNISENDER_GO_API_KEY=...
UNISENDER_GO_API_URL=https://goapi.unisender.ru/ru/transactional/api/v1
EMAIL_FROM=noreply@mail.okno.business
EMAIL_FROM_NAME=okno.business
EMAIL_REPLY_TO=support@okno.business
# Закрывает ручной роут отправки: openssl rand -hex 32
UNISENDER_WEBHOOK_SECRET=...
```

5. **Миграция БД:** `supabase/migrations/202608050001_notification_log.sql`.
6. **Проверка ключа и домена:**

```bash
npm run email:test
```

Без адреса скрипт только пингует API и печатает статусы доменов. С адресом —
ещё и шлёт диагностическое письмо:

```bash
npm run email:test -- support@okno.business
```

7. **Регистрация вебхука:**

```bash
npm run email:webhook
```

Адрес — `NEXT_PUBLIC_APP_URL/api/webhooks/unisender`. Посмотреть текущие:
`npm run email:webhook -- --list`, снять: `npm run email:webhook -- --delete`.

## Порядок проверки

1. `npm run email:test` — ключ принят, домен готов.
2. `npm run email:test -- support@okno.business` — письмо на свой домен.
   Чужие и случайные адреса на этом шаге не трогать: невалидный адрес портит
   репутацию домена с первого дня.
3. `npm run email:webhook` — вебхук зарегистрирован.
4. Письмо через приложение (полный шаблон, запись в журнал):

```bash
curl -X POST https://okno.business/api/email/test \
  -H "Authorization: Bearer $UNISENDER_WEBHOOK_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"to":"support@okno.business"}'
```

5. Строка в `notification_log`: сначала `queued`, через несколько секунд
   `delivered`, после открытия — `opened`.
6. Письмо на Яндекс/Gmail — в заголовках полученного письма должны быть
   `spf=pass`, `dkim=pass`, `dmarc=pass`.

## Журнал писем

`notification_log` — одна строка на письмо, живущая всё время его жизни:
`queued` при отправке, дальше `sent → delivered → opened → clicked` по мере
вебхуков. Пара `(job_id, recipient)` уникальна, событие ищет строку по ней.

**Статус не откатывается назад.** Порядок вебхуков не гарантирован, `delivered`
легко приходит после `opened`. Поэтому у статусов есть числовой вес
(`notification_status_weight`), и запись двигается только вперёд. Исключения:

- `spam` и `hard_bounced` применяются всегда — окончательный приговор важнее
  любого «прочитано»;
- `unsubscribed` и `subscribed` переключают друг друга в обе стороны, у них
  одинаковый вес, и побеждает событие с более поздним `event_time`;
- `soft_bounced` стоит между `sent` и `delivered`: это временная недоставка,
  Unisender Go двое суток пробует снова и письмо ещё может дойти.

`last_event_at` двигается только вместе с применённым статусом. Иначе
отброшенное событие с поздним временем и низким весом сдвигало бы отметку
вперёд, и следующая настоящая отписка проигрывала бы тайбрейк событию, которого
в журнале нет.

Вся логика — внутри процедуры `record_notification_event`, одним оператором:
иначе «прочитать статус → сравнить веса → обновить» разъезжается между
параллельными вебхуками.

Событие может прийти раньше, чем завершится запись при отправке. Тогда строку
создаёт вебхук, а отправка дозаполняет тему и тип письма. Тип на этот случай
дублируется в метаданных (`metadata.email_type`) — вебхук больше ниоткуда его
не узнает.

RLS включён, политик нет: журнал читает и пишет только сервисная роль.
Политику на чтение из админки добавим, когда появится роль админа в БД.

## Отписка и трекинг

По умолчанию Unisender Go подставляет в HTML блок со ссылкой отписки,
переписывает ссылки на трекинговые и вставляет пиксель отслеживания открытий.

Для служебных писем это лишнее, но **`skip_unsubscribe=1`, `track_links=0` и
`track_read=0` нельзя передавать, пока техподдержка не включит такую
возможность для аккаунта** — запрос вернёт ошибку. Заявка:
https://go2.unisender.ru/ru/support

В коде эти три поля уже заложены под флаг `transactional` в `sendEmail` и по
умолчанию не отправляются вовсе. После разрешения достаточно передавать
`transactional: true` для служебных писем — маркетинговые продолжат идти с
отпиской и трекингом.

## Что важно помнить

- **HTTP 200 — это не доставка.** Ответ `email/send.json` означает только приём
  в очередь. Реальный статус приносит вебхук.
- **`failed_emails` приходит и при 200.** Адрес мог быть отписан, невалиден или
  заблокирован. Такие случаи уходят в лог отдельным предупреждением, а не
  теряются внутри «письмо отправлено».
- **Идемпотентность.** Для писем, привязанных к событию, передавай
  `idempotenceKey` вида `booking-confirm-<id>`: повтор с тем же ключом в течение
  минуты отклоняется, и ретрай не превращается в дубль письма клиенту. API-код
  `1573` — это как раз «уже отправляли», клиент помечает его `duplicate: true`,
  а не ошибкой доставки. У ручной проверки ключа нет намеренно: её запускают
  подряд по несколько раз.
- **Ретраи.** `429` и `50x` повторяются трижды с задержками 1/2/4 секунды.
  Остальные `4xx` не повторяются: это ошибка запроса.
- **Лимиты.** До 500 получателей и 10 МБ на запрос, максимум 4 метки по 50
  символов, до 10 ключей метаданных (ключ до 64 символов, значение до 1024).
  Имена подстановок — только латиница, цифры и `_`, первый символ буква.
  Всё это проверяется в `sendEmail` до похода в сеть.

## Безопасность

- **Подлинность вебхука.** Unisender Go кладёт в тело поле `auth` — MD5 от
  этого же тела, в котором значение `auth` заменено на API-ключ. Роут считает
  хеш по исходной строке запроса (не по пересериализованному JSON, иначе хеш
  другой) и сравнивает за константное время. Отдельный секрет вебхуку не нужен,
  подпись заодно подтверждает целостность.
- **Ответ за 3 секунды.** Unisender Go ждёт 200 в течение трёх секунд, иначе
  начинает повторять пакет. Запись в базу уходит в `after()` из `next/server` —
  ответ отдаётся сразу, обработка идёт после него. Именно `after()`, а не
  `waitUntil` из `@vercel/functions`: приложение живёт на своём node-сервере
  под systemd, где вызов Vercel-примитива просто не сработает.
- **Роут отправки закрыт.** `POST /api/email/test` требует
  `Authorization: Bearer $UNISENDER_WEBHOOK_SECRET`, сверка за константное
  время. Без секрета в окружении роут отвечает 503. Открытый эндпоинт,
  рассылающий письма по переданному адресу, — это спам-релей.
- **Ключ только на сервере.** Никаких `NEXT_PUBLIC_` префиксов: с ключом можно
  слать письма от имени домена.
