# Чеки НПД: автоотправка в «Мой налог»

ЮKassa закрыла свой сервис автоматической передачи чеков самозанятым, поэтому
доход платформы регистрируется в личном кабинете ФНС (`lknpd.nalog.ru`) нашим
кодом.

Логика портирована из [grandvan709/yookassa-to-mynalog](https://github.com/grandvan709/yookassa-to-mynalog)
(Apache-2.0): те же эндпоинты кабинета, та же форма запросов и тот же приём с
поиском уже выбитого чека после оборванного ответа. Отличия — очередь в
Postgres вместо файла состояния, вебхук вместо опроса ЮKassa по платежам и
фоновая job вместо контейнера с cron.

## Что попадает в чек

Только собственный доход платформы — то, что мастер платит **нам** за сервис:

| Поток | Источник | Наименование в чеке |
|---|---|---|
| Подписка PRO | `subscription_payments` | `okno «<тариф>» — подписка на N дней` |
| Доплата за места в команде | `subscription_payments` (`kind='seat'`) | `okno — оплата мест в команде (N)` |

К наименованию добавляется хвост платежа ЮKassa: `…, платёж 3f4a1b`. Это не
украшение — на нём держится защита от двойного чека (см. ниже).

## Что в чек не попадает и попасть не должно

Деньги клиентов — **предоплата, чаевые, подарочные сертификаты** — доходом
платформы не являются. Они идут в магазин ЮKassa самого мастера, напрямую на
его счёт; сервис их не принимает, не хранит и не перечисляет, платёжным
агентом не является (`PRODUCT.md`, раздел «Деньги»;
`okno-functional-description.md`, п. 7.2). Чеки по ним выбивает мастер со
своего аккаунта НПД.

Чаевые вдобавок переезжают на CloudTips (`okno-todo.md`) — после переноса
платформа их не увидит вовсе.

> **Расхождение кода с моделью, к чекам отношения не имеющее.** Сейчас
> `src/app/actions/tips.ts` и `src/app/actions/gift-certificates.ts` создают
> платёж через `createYooKassaPayment`, то есть ключами **платформы**, а не
> OAuth-токеном мастера, как предоплата в `src/app/api/bookings/route.ts`.
> Для чаевых это известный незакрытый пункт, для сертификатов — похоже, просто
> не переведено. Пока это так, деньги физически приходят в магазин платформы,
> и расхождение с офертой надо закрывать в самом платёжном коде, а не
> компенсировать чеками НПД: выбивать их здесь значило бы признать эти деньги
> нашим доходом.

## Переменные окружения

```bash
# ИНН, он же логин в кабинете. Нужен всегда: входит в ссылку на чек.
NALOG_INN=910924469701

# Способ входа: password (по умолчанию) или refresh
NALOG_AUTH_METHOD=password

# password: пароль от личного кабинета налогоплательщика ФНС
NALOG_PASSWORD=...

# refresh: если кабинет заведён через Госуслуги и пароля не существует
# NALOG_AUTH_METHOD=refresh
# NALOG_REFRESH_TOKEN=...
# NALOG_DEVICE_ID=...            # тот же, из которого получен токен

# Шифрование refreshToken в базе. Обязателен в режиме refresh.
# openssl rand -hex 32
NALOG_ENCRYPTION_SECRET=...

# Необязательно: какие потоки выбивают чек (по умолчанию оба)
# NALOG_SOURCES=subscription,seat

# Необязательно: прокси, если приложение живёт за пределами РФ
# NALOG_PROXY_URL=socks5://user:pass@host:1080
```

Пока `NALOG_INN` и способ входа не заданы, вся подсистема выключена: платежи
проходят как обычно, просто ни одна строка не встаёт в очередь на чек.

### Как достать refreshToken и deviceId

Нужно только в режиме `refresh` (вход через Госуслуги).

1. Зайти в `lknpd.nalog.ru` в браузере.
2. DevTools → Network → фильтр по `token`.
3. В запросе `POST /api/v1/auth/token` взять из тела `refreshToken` и
   `deviceInfo.sourceDeviceId`.

`deviceId` менять нельзя — кабинет привязывает сессию к нему. Кабинет
ротирует `refreshToken` при каждом обновлении: живое значение переезжает в
`nalog_sync_state.refresh_token_encrypted`, а строка в `.env` после первого
успешного входа становится историей. Это нормально и так и задумано —
восстановить её значение обратно из базы нельзя без `NALOG_ENCRYPTION_SECRET`.

## Миграция БД

```bash
supabase db push
# или вручную: supabase/migrations/202608060001_nalog_receipts.sql
```

Появятся две таблицы:

* `nalog_sync_state` — deviceId, зашифрованный refreshToken, курсор
  просмотренных возвратов. Одна строка, `id='platform'`.
* `nalog_receipts` — очередь и журнал чеков. `unique(provider_payment_id)`
  держит главный инвариант: один платёж — один чек.

## Cron

```cron
*/10 * * * * curl -s -X POST -H "x-jobs-secret: $JOBS_SECRET" https://okno.business/api/jobs/nalog-receipts > /dev/null
```

`POST /api/jobs/nalog-receipts` делает две вещи подряд:

1. **Выбивает чеки** по строкам очереди, у которых подошло время попытки.
2. **Аннулирует чеки** по возвратам: опрашивает `/v3/refunds` ЮKassa начиная
   с сохранённого курсора и гасит чек по каждому найденному возврату.

Раз в десять минут — с запасом: по безналичным расчётам чек НПД формируется
не позднее 9-го числа следующего месяца (ч. 3 ст. 14 422-ФЗ), так что
задержка в минутах роли не играет, зато очередь не копится.

Запускать параллельно в нескольких экземплярах безопасно, но бессмысленно:
кабинет ФНС не любит частых запросов, а строки очереди берутся пачками по 20.

## Как это работает

```
вебхук ЮKassa (succeeded)
        │
        ▼
queueNalogReceipt() ──► nalog_receipts (status=pending)
                                │
                    /api/jobs/nalog-receipts (каждые 10 мин)
                                │
                    ┌───────────┴────────────┐
                    ▼                        ▼
            POST /api/v1/income      GET /v3/refunds → POST /api/v1/cancel
                    │
              status=registered, receipt_uuid, receipt_url
```

Чек ставится в очередь, а не выбивается прямо из вебхука, по двум причинам:
кабинет ФНС падает и тормозит заметно чаще нашего приложения, а вебхук ЮKassa
обязан ответить быстро, иначе она начнёт слать повторы.

Подписка встаёт в очередь не в самом вебхуке, а в
`applySubscriptionPaymentResult` — туда же приходит подборщик зависших
платежей и автосписание, и чек нужен по каждому из этих путей.

### Защита от двойного чека

Лишний доход в НПД снимается только руками, поэтому дублей не должно быть в
принципе. Рубежи:

1. `unique(provider_payment_id)` — повторный вебхук по тому же платежу не
   создаёт вторую строку.
2. **Захват строки.** Перед походом в кабинет строка помечается «в работе» на
   5 минут одним атомарным `update … where next_attempt_at <= now()`. Два
   пересёкшихся прогона job не возьмут один платёж.
3. **Счётчик попыток растёт до похода в кабинет,** а не по результату. Иначе
   упавшая ровно между выбитым чеком и записью результата база оставила бы
   `attempts=0`, и следующий прогон пошёл бы выбивать чек заново.
4. **Поиск уже выбитого чека.** Перед повторной попыткой (`attempts > 0`) и
   сразу после ошибки `POST /income` выполняется поиск в кабинете по
   наименованию и сумме за 7 дней: кабинет умеет провести доход и оборвать
   ответ. Хвост платежа в наименовании делает строку различимой — без него
   два мастера, купившие один тариф в одну неделю, дали бы одинаковые чеки, и
   поиск закрыл бы вторую строку чужим номером, занизив доход.
5. **Найденный чек принимается, только если его номер ещё ни за кем не
   закреплён** — плюс `unique(receipt_uuid)` в базе как последний рубеж.

### Повторы и отказ

Паузы между попытками: 1, 5, 15, 60, 240, 720, 720 минут. После 8 неудач
строка получает `status='failed'`, в журнал аудита пишется
`nalog.receipt.failed` — дальше чек выбивается руками в кабинете.

Ошибка входа (сменили пароль, отозвали токен) прерывает весь прогон: время
следующей попытки у остальных строк не сдвигается, и после починки доступа
они уйдут в кабинет сразу.

### Возвраты

Возврат по платежу платформы делается руками в кабинете ЮKassa — никакого
события в нашем коде при этом не происходит, поэтому единственный способ
узнать о нём — опрос `/v3/refunds`. Полный возврат гасит чек автоматически
(`comment: "Возврат средств"`).

Курсор просмотренных возвратов двигается только после полного обхода без
единой ошибки: ЮKassa отдаёт список от свежих к старым, и сдвиг после обрыва
спрятал бы непросмотренные возвраты навсегда — то есть налог начислился бы на
возвращённые деньги. Повторный разбор безвреден, аннулирование идемпотентно.

**Частичный возврат не обрабатывается автоматически.** В «Моём налоге» чек
нельзя уменьшить: правильный путь — аннулировать старый и выбить новый на
остаток, а ошибка здесь стоит лишнего налога и разбирательства с ФНС. Такой
возврат пишет в аудит `nalog.receipt.partial_refund` и ждёт человека.

## Проверка

```bash
npm run nalog:check            # только вход в кабинет
npm run nalog:check -- --incomes   # плюс чеки за последние 7 дней
```

Скрипт ничего не выбивает и не аннулирует. В режиме `refresh` он читает токен
из `.env`, а не из базы, — если приложение уже работало, значение в файле
протухло, и отказ входа тут ожидаем.

Дальше:

1. Оплатить подписку тестовым платежом → строка в `nalog_receipts` со
   статусом `pending`.
2. Дёрнуть job руками:
   ```bash
   curl -s -X POST -H "x-jobs-secret: $JOBS_SECRET" https://okno.business/api/jobs/nalog-receipts
   ```
   Ответ: `{"ok":true,"receipts":{"registered":1,...},"refunds":{...}}`.
3. Строка получает `status='registered'`, `receipt_url` открывает печатную
   форму чека.

## Ограничения, о которых стоит знать

* **Плательщик считается физлицом.** В запрос уходит
  `incomeType: "FROM_INDIVIDUAL"`. Если подписку оплатит ИП или юрлицо,
  налоговая формально ждёт `FROM_LEGAL_ENTITY` с ИНН плательщика — а ЮKassa
  ИНН плательщика не отдаёт. Отдельного поля для этого в кабинете мастера
  тоже нет, так что различить такие оплаты сейчас нечем.
* **`paymentType: "CASH"`.** Отдельного типа для эквайринга в API кабинета не
  существует; веб-кабинет для поступлений на карту отправляет то же самое.
* **IP-фильтр ФНС.** Кабинет отвечает только на российские адреса. Если
  приложение переедет на зарубежный хостинг — `NALOG_PROXY_URL` плюс
  `npm i undici` (пакет подключается лениво и только под прокси).
* **Лимит дохода НПД — 2,4 млн ₽ в год.** При превышении кабинет откажет в
  регистрации дохода, строки уйдут в `failed`, и дальше это уже вопрос смены
  налогового режима, а не кода. `ignoreMaxTotalIncomeRestriction` мы шлём
  `false` — молча пробивать лимит нельзя.
* **Чеки мастеров не выбиваются.** Подсистема одноарендная: один аккаунт ФНС
  на платформу. `nalog_sync_state.id` заведён под будущие аккаунты мастеров,
  но хранить пароли от чужих кабинетов ФНС — отдельное решение с отдельной
  ценой, и сейчас оно не принято.
